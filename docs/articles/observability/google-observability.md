# Observability и Monitoring в Google: эволюция подходов

## Введение

Google — одна из первых компаний, столкнувшихся с проблемой наблюдения за распределёнными системами на планетарном масштабе. Многие концепции, которые сейчас считаются стандартными в observability (time-series мониторинг, распределённая трассировка, SRE-практики), были разработаны внутри Google. Этот текст прослеживает эволюцию их подходов — от ранних скриптов к Borgmon, Dapper, Monarch и современной Google Cloud Observability.

---

## 1. Эпоха до Borgmon: администрирование вручную (до 2003)

В начале 2000-х в Google мониторинг строился на классической модели того времени:

- **Custom check scripts:** разработчики писали скрипты, которые проверяли ответы сервисов (HTTP-статус, время ответа, содержание ответа).
- **Nagios-style alerting:** скрипты выдавали OK/WARNING/CRITICAL, запускали алерты при выходе за пороги.
- **Разделение мониторинга и визуализации:** скрипты жили отдельно от систем отрисовки графиков (RRDtool, MRTG). Один инструмент — для алертов, другой — для трендов.

**Проблемы** этой модели при росте масштаба:
1. Каждый скрипт — отдельный процесс, запуск которого на тысячах машин создаёт неприемлемую нагрузку (fork + exec + network connection setup для каждой проверки).
2. Невозможность задать коррелирующие запросы уровня «покажи latency по всем бэкендам, сгруппированный по версии бинарника».
3. Данные теряются между циклами сбора — нельзя посмотреть историю для ретроспективы.

## 2. Borgmon (2003–2015)

С созданием Borg (кластерного менеджера, предшественника Kubernetes) в 2003–2004 появилась потребность в мониторинге, который понимает топологию кластера: динамические target'ы, масштабирование, автоматическое восстановление.

### Архитектура Borgmon

Borgmon ввёл несколько революционных идей, которые потом легли в основу Prometheus:

**Pull-модель сбора:** Borgmon сам запрашивает метрики у target'ов (pull), а не ждёт, пока target'ы что-то отправят (push). Target'ы предоставляют `/varz` HTTP-endpoint, который возвращает все метрики одним запросом. Один HTTP-запрос заменяет сотни скриптов.

**Формат varz:** текстовый, schemaless. Каждая строка — `переменная значение` или `переменная map:ключ1:значение1 ключ2:значение2`. Любой разработчик может добавить метрику одной строкой кода. Это крайне низкий порог для инструментирования.

**Time-series как first-class концепция:** Все собранные данные хранятся в виде time-series (имя + labels → последовательность `(timestamp, value)`). Это позволяет не просто проверять «жив ли сервис», а строить *векторные* запросы — операции над целыми наборами time-series.

**In-memory хранение:** Данные хранятся в RAM (time-series arena) с контрольными точками на диск. Типичный horizon — 12 часов в памяти, до нескольких недель в TSDB (Time-Series Database — дисковое расширение).

**Rule evaluation engine:** Borgmon — это, по сути, программируемый вычислитель time-series. Правила записываются на специальном языке правил, который позже стал образцом для PromQL.

**Иерархия Borgmon:** Один Borgmon может собирать данные с target'ов, а другой Borgmon — с первого Borgmon. Это позволяет строить иерархии: scraper-level → cluster-level → global-level, на каждом уровне агрегируя и отбрасывая часть кардинальности.

**Synthetic variables:** Borgmon автоматически добавляет переменные для каждого target'а: alive, responded, collection_time. Это позволяет писать правила для детектирования недоступности без дополнительной инструментации.

### Проблемы Borgmon

Несмотря на новаторство, Borgmon имел недостатки:

1. **In-memory хранение с фиксированным horizon:** 12 часов в RAM — хорошо для алертов, но плохо для долгосрочного анализа трендов.
2. **Single point of failure:** если Borgmon падает — теряется in-memory arena (до checkpoint на диск).
3. **Масштабирование кардинальности:** работало для Google, но требовало значительных ресурсов. Один Borgmon на кластер может быть узким местом.
4. **Схемы нет:** varz — текстовый формат без схемы. Изменение переменной требует согласования с правилами, а механизма валидации нет. На практике это приводило к сломанным алертам после рефакторинга кода.

В Google SRE Book (гл. 10) про Borgmon написано:
> "В ретроспективе очевидно, что этот бессхемный текстовый интерфейс создаёт низкий порог для инструментирования, что хорошо для инженерной культуры. Однако это ухудшает долгосрочную поддерживаемость."

### Влияние на индустрию

Borgmon стал прямым предшественником SoundCloud **Prometheus** (2012), который унаследовал pull-модель, time-series как first-class, varz-формат метрик, иерархию collection tiers и язык правил (PromQL = потомок Borgmon rule language).

## 3. Dapper: распределённая трассировка (2010)

Dapper — распределённая трассировочная система Google, описанная в техническом отчёте 2010 года (Benjamin H. Sigelman et al., "Dapper, a Large-Scale Distributed Systems Tracing Infrastructure").

### Мотивация

Для распределённых систем (Google Search, Ads, Gmail) один запрос может породить сотни внутренних RPC между тысячами машин. Традиционные метрики (latency, error rate) не позволяют понять, *какой именно* сервис в causal path запроса вызвал замедление.

### Ключевые дизайнерские решения

**Annotation-based tracing (не black-box):** Dapper использует явное проставление trace_id и span_id в контекст каждого RPC. Это требует инструментирования библиотек, но даёт точные трассировки без статистических погрешностей black-box методов.

**Инструментирование на уровне общих библиотек:** Dapper не требует от разработчиков писать код для трассировки. Вся инструментация встроена в RPC-фреймворк, threading library и control flow library. Поскольку почти весь код в Google использует эти общие библиотеки, трассировка работает «бесплатно».

**Низкий overhead:** Основной механизм — *адаптивное семплирование*. По умолчанию трассируется только 1 запрос из 1000 (0.1%). При обнаружении медленного трейса (latency > threshold) семплирование увеличивается. Экспериментально подтверждено, что для большинства use cases достаточно одной пробы из тысяч — распределения восстанавливаются статистически.

**Два-host spans:** Каждый RPC-span содержит аннотации и с клиента, и с сервера. Это позволяет детектировать clock skew между машинами и корректировать timing.

### Структура данных

- **Trace** — дерево интервалов работы, объединённых общим trace_id.
- **Span** — базовая единица. Содержит span_id, parent_span_id, имя (человекочитаемое), тайминги, аннотации.
- **Annotation** — произвольные ключ-значение-таймстемп, добавляемые разработчиком при необходимости (application-specific).

### Роль Dapper

Dapper стал платформой, на которой построены десятки инструментов анализа, не предусмотренных его создателями:
- Визуализация трейсов (waterfall view).
- Совокупный анализ latency (statistical profiling по трейсам).
- Детекция медленных путей (slowest paths).
- Поиск по атрибутам трейсов.

Это породило концепцию **«tracing as a platform»** — идею, что данные трассировки можно использовать не только для единичной отладки, но и для агрегированного анализа производительности.

Dapper оставался внутренней инфраструктурой Google, но его идеи легли в основу OpenTracing (2015, Ben Sigelman — один из авторов Dapper), а затем OpenTelemetry.

## 4. От Borgmon к Monarch (2010–2020)

К 2010-м годам масштаб Google превысил возможности Borgmon. Требовалась система, работающая на **планетарном уровне** (глобально-распределённые дата-центры) с высокой надёжностью и горизонтальной масштабируемостью.

### Monarch (публикация: VLDB 2020)

Monarch — это глобально-распределённая in-memory time-series база данных, работающая как multi-tenant сервис. Каждую секунду она записывает **терабайты time-series данных** в память и отвечает на **миллионы запросов**.

Ключевые архитектурные решения:

**Региональная архитектура:** Monarch разделён на регионы (по географическому расположению дата-центров). Каждый регион независим — если один регион выходит из строя, остальные работают. Данные реплицируются между регионами.

**Global query and configuration plane:** Monarch предоставляет единую глобальную точку для запросов (через global query plane), которая агрегирует данные со всех регионов. Конфигурация метрик (что собирать) задаётся глобально и распространяется на регионы.

**Два уровня хранения:**
1. **In-memory (быстрый, «горячий»):** последние минуты/часы данных. Используется для алертов, дашбордов и ad-hoc запросов.
2. **Cold storage (дисковый):** данные старше нескольких часов, которые редко запрашиваются, но доступны при необходимости.

**Multi-tenancy:** Monarch — shared сервис. Все команды Google используют один и тот же Monarch. Изоляция через namespaces и квоты.

**Масштабирование:** Горизонтальное. Новые регионы добавляются как отдельные shards, global query plane знает о них.

### Разница между Borgmon и Monarch

| Аспект | Borgmon | Monarch |
|--------|---------|---------|
| Масштаб | Кластер (сотни машин) | Планетарный (сотни дата-центров) |
| Хранение | In-memory (12ч) + TSDB | In-memory + cold storage |
| Надёжность | SPOF | Региональная избыточность |
| Multi-tenancy | Нет | Да |
| Язык правил | Borgmon rule language | Множественные языки (через API) |

### Мониторинг в стиле SRE (2015–2016)

Параллельно с развитием инфраструктуры сбора данных, Google SRE team формализовала **подходы к мониторингу и алертингу**. Ключевые публикации:

**SRE Book (2016):**
- Четыре золотых сигнала: **Latency, Traffic, Errors, Saturation** (задержка, трафик, ошибки, насыщенность).
- Различие между **white-box и black-box мониторингом**.
- Иерархия Production Needs (мониторинг — фундамент).
- Концепция **SLI/SLO/SLA** → Service Level Indicator (измеряемая метрика), Service Level Objective (целевой порог), Service Level Agreement (юридическое обязательство). SLO-ориентированный подход к мониторингу: не каждый выброс — инцидент, только когда нарушается SLO.

**SRE Workbook (2018):**
- Практические рецепты: как строить мониторинг, как писать устойчивые правила (resilient alerts), как разрабатывать SLO-based алерты.

## 5. Google Cloud Observability и Stackdriver (2017–н.в.)

После создания Google Cloud Platform возникла потребность предоставить пользователям GCP инструменты наблюдения. Stackdriver был запущен как managed сервис мониторинга, логирования и трассировки.

**Эволюция названий и компонентов:**
- **Stackdriver Monitoring** (2015) — собран на технологии Monarch, адаптированной для облачных клиентов.
- **Stackdriver Logging** (2014, позже Cloud Logging) — централизованное хранилище логов с query language.
- **Stackdriver Trace** (2017) — распределённая трассировка на идеях Dapper, адаптированная для GCP.

С 2020 года Stackdriver переименован в **Google Cloud Observability**, объединив Cloud Monitoring, Cloud Logging, Cloud Trace, Error Reporting, Profiler.

**Google Cloud Profiler** (2017) — continuous profiling в production. Собирает CPU и heap profiles из работающих приложений без остановки. Показывает flame graphs «какая функция сколько ресурсов потребляет». Открыт как внутренний инструмент Google, затем выпущен как продукт GCP.

**Google Cloud Operations Suite** — текущий зонтичный бренд для всех observability-продуктов Google Cloud.

## 6. Современные внутренние практики Google

### Структурированные логи (Canonical Log Lines / Wide Events)

Внутри Google широко используется практика **canonical log lines** — одной структурированной лог-строки на запрос, содержащей все ключевые атрибуты бизнес-контекста. Это по сути wide events, хотя Google не использует этот термин в своих публичных документах так часто, как Honeycomb.

Формат: каждая строка — JSON или Protocol Buffers, с десятками полей: `request_id`, `service`, `endpoint`, `user_id`, `duration_ms`, `status_code`, `backend_count`, `cache_hit`, etc.

### Инструментирование

Google требует инструментирования всех сервисов с использованием внутренних SDK, которые автоматически:
- Предоставляют метрики latency, QPS, error rate для каждого API.
- Проставляют trace context во все RPC-вызовы.
- Добавляют canonical log line на каждый запрос.

### OpenTelemetry

Google — один из ключевых контрибьюторов OpenTelemetry (наряду с LightStep/Ben Sigelman и Microsoft). С 2019 года Google Cloud Observability поддерживает OTLP (OpenTelemetry Protocol) как нативный формат приёма данных.

### Четыре золотых сигнала

В SRE Book (гл. 6) сформулированы четыре сигнала, которые Google считает минимально достаточным набором для мониторинга любого сервиса:

1. **Latency** — время ответа.
2. **Traffic** — объём запросов.
3. **Errors** — доля ошибочных ответов.
4. **Saturation** — степень утилизации ресурсов.

Если покрыты все четыре, можно обнаружить и диагностировать подавляющее большинство проблем с производительностью и доступностью сервиса. Рассмотрим каждый.

---

#### Latency (задержка) — что это и почему покрывает «всё»

**Измеряемая величина:** распределение времени обработки запроса. Не среднее (mean), а *перцентили*: p50 (медиана), p95, p99, p99.9.

**Почему распределение, а не среднее:**
- Среднее скрывает аномалии: если 99% запросов выполняются за 1ms, а 1% — за 10s, среднее будет ~100ms, и проблема выглядит как «чуть больше нормы».
- p99 показывает, что испытывает самый медленный пользователь. Это важно: для пользователя latency — это «сколько я жду», а не «сколько в среднем ждут».
- SRE-практика Google: p95 — стандарт для дашбордов, p99 — для алертов, p99.9 — для инфраструктурных компонентов.

**Что даёт измерение latency:**
- Любая деградация сервиса почти всегда проявляется в росте latency. Будь то перегрузка CPU, проблема с сетью, медленный SQL-запрос, исчерпание пула соединений, GC pause в JVM — всё это увеличивает время обработки запроса.
- **Обратное неверно:** latency показывает *наличие* проблемы, но не *причину*. Рост latency — это симптом, а не диагноз. Однако симптом уже достаточен для алерта: мы знаем, что что-то не так.
- Latency — **самый чувствительный из четырёх сигналов**. Если что-то ломается, latency меняется первой. Остальные три сигнала нужны, чтобы отделить *категорию* проблемы.

---

#### Traffic (трафик) — контекст для остальных сигналов

**Измеряемые величины:**
- RPS (requests per second) или QPS (queries per second).
- Часто разбивается по типам запросов (read vs write, API endpoint), по источникам (внутренний клиент A vs B).

**Роль:**
- Traffic — это **базовый контекст для интерпретации остальных сигналов**. Рост latency может быть вызван ростом traffic (нормально) или без изменения traffic (проблема).
- Traffic в комбинации с error count даёт error rate — ключевой перцентиль для SLO.
- Traffic определяет budget для резервирования (capacity planning).
- **Почему покрывает большую часть:** traffic-пики — причина большинства инцидентов «внезапно стало медленно» (flash crowd, DDOS, партнёр начал слать в 10x больше запросов).

---

#### Errors (ошибки) — быстрая категоризация проблем

**Измеряемые величины:**
- Error rate: доля ответов с HTTP 5xx, 4xx (если это бизнес-ошибки), или любое несоответствие expected behavior.
- Явные ошибки: явные исключения, таймауты.
- Неявные ошибки: успешный HTTP 200 с неправильным содержимым (например, пустой список результатов), «тихие» ошибки (молчаливый drop запроса).

**Почему errors — третий по ценности сигнал:**
- Они дают **бинарную категоризацию**: если error rate + latency растут одновременно, проблема, скорее всего, в сервисе (регрессия, баг). Если latency растёт, а error rate нет — проблема, скорее всего, в ресурсной насыщенности (saturation) или внешнем факторе.
- Это **краеугольный камень SLO**: подавляющее большинство SLO определяются через комбинацию latency + error rate.
- Errors в отдельности не говорят о производительности. Сервис может быть быстрым, но возвращать ошибки. Поэтому errors без latency — неполная картина.

---

#### Saturation (насыщенность) — раннее предупреждение до того, как что-то сломалось

**Измеряемые величины:**
- CPU utilisation (обычно средняя за 1–5 минут).
- Memory utilisation.
- I/O utilisation (дисковая очередь, IOPS, bandwidth).
- Network utilisation (bandwidth, packet drops, retransmits).
- **Специфичные для сервиса грейды:** thread pool utilisation, connection pool utilisation, in-flight request count, GC overhead, file descriptor usage.

**Ключевое отличие от latency и errors:**
- Latency и errors — **симптомы** уже случившейся проблемы для пользователя.
- Saturation — **предвестник** проблемы. Когда utilisation пересекает порог (обычно 60–70% для production), latency начинает расти экспоненциально, но пользователь этого ещё не замечает.

**Золотое правило Google (из SRE Book):**
> "Utilisation must be measured at the most constrained resource." Если узкое место — CPU, смотреть CPU utilisation. Если база данных — IOPS. Если воркеры — pool size utilisation.

**Пример:** при 50% CPU utilisation latency стабильна. При 80% latency растёт на 20% для p95. При 95% latency может вырасти в 10–50x (из-за contention, scheduling latency, GC). Алерт по CPU utilisation на 70–80% даёт время на реакцию до того, как latency станет заметна пользователю.

---

#### Почему эти четыре сигнала минимально достаточны

В SRE Book (гл. 6) даётся элегантный аргумент: **любая проблема в сервисе проявляется как изменение хотя бы одного из четырёх сигналов.** Доказательство от противного:

1. Если сервис работает (traffic есть), но данные не приходят вовремя (latency растёт) — проблема в самом сервисе или его зависимостях. Error rate и saturation помогут отличить *что именно*.
2. Если сервис работает долго, но ошибается (error rate растёт, latency может быть в норме) — проблема в корректности (баг, несовместимость данных).
3. Если сервис медленный (latency растёт), но не перегружен (saturation не изменилась) и не ошибается (errors не растут) — проблема в *upstream зависимости* (вызываемый сервис медленный). Определяется через latency breakdown.
4. Если сервис перегружен (saturation растёт) — latency неизбежно начнёт расти (через нелинейную зависимость). Если начинать с saturation, можно предотвратить latency.
5. Если нет traffic — сервис может быть мёртв, либо у него нет клиентов (баг в клиенте, отключена интеграция). Traffic измеряется всегда, и отсутствие traffic — тоже сигнал.

**Исключения — что не покрывают четыре сигнала:**
- **Тихие ошибки:** сервис отвечает быстро, без ошибок, но возвращает неправильные данные (например, некорректное значение поля). Покрывается дополнительными тестами корректности (data quality monitoring) или wide events с бизнес-семантикой.
- **Проблемы «не в этом сервисе»:** четыре сигнала сервиса A не покажут, что проблема в сервисе B (если только A не вызывает B). SRE практикует *dependency monitoring* (health check для каждого upstream).
- **Медленная деградация:** рост latency на 0.1% в день не запустит алерт, но через год даст +40%. Это покрывается трендовым анализом (например, weekly p50 trend с порогом год к году).

Четыре золотых сигнала — это **мониторинг**, а не observability (см. шкалу сырости). Они отвечают на заранее известные вопросы («не растёт ли latency», «не превысил ли error rate SLO»). Для ответа на не известные заранее вопросы нужны данные левее на шкале — wide events.

## 7. Специфические проблемы Google

### Масштаб

Google обрабатывает миллиарды запросов в секунду. Это означает:
- Невозможно хранить *все* трейсы — семплирование обязательно.
- Невозможно хранить *все* логи — фильтрация на записи.
- Time-series системы должны быть планетарно-распределёнными и отказоустойчивыми.

### Разнородность стеков

Внутри Google используются C++, Java, Go, Python, Rust. Каждый язык — своя runtime, свой способ инструментирования. Единый подход (RPC-фреймворк + общие библиотеки) позволяет сохранять прозрачность трассировки, но требует поддержки для каждого языка.

### PII и безопасность

Логи могут содержать персональные данные пользователей. Google применяет автоматические фильтры PII на записи (scrubbing), чтобы избежать утечек в центральное хранилище логов.

### Избыточность против экономности

Google может позволить себе гигантские объёмы хранения (Monarch in-memory — терабайты). Но даже для Google есть бюджетные ограничения. Постоянная оптимизация: что хранить hot, что cold, что отбрасывать.
